# v2 升级说明

本次升级围绕三件事：**修掉工程硬伤**、**实现可溯源引用**、**加上登录与多用户隔离**。
下面是每一项的动机、做法和实测数据。

---

## 一、为什么要升级

v1 能跑通，但存在几个会被评审或答辩直接问到的问题：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 向量模型用的是 `paraphrase-MiniLM-L6-v2`（2021 年的英文小模型） | 对中文文献检索基本失效，问答质量靠运气 |
| 2 | 模型加载失败只打印一行日志，然后静默退化成"取前 5 段" | 用户完全无感，答案质量暴跌却不知道 |
| 3 | `llm_integration.py` 里的兜底回答是从别的项目抄来的 | API 异常时会输出"工作电压窗口 1.8V""能量密度 0.40 mWh cm⁻³"等与本文献毫无关系的内容 |
| 4 | `app.py` 和 `ai_functions.py` 各自加载一份模型 | 白占约 90MB 内存，首次提问更慢 |
| 5 | 分块按 500 字符硬切，页码在解析阶段就丢了 | **无法给出任何出处**，学术工具的核心价值缺失 |
| 6 | 没有登录，没有用户隔离 | 谁打开网页都能看见、删掉所有人的文献 |
| 7 | 前端依赖 3 个国外 CDN（Tailwind / FontAwesome / pdf.js） | 断网或校园网不稳时页面直接白板 |
| 8 | 没有流式输出，摘要要白等 30~60 秒 | 演示体验差 |

---

## 二、做法

### 1. 换向量模型 + 修静默降级

- 模型换成 **`Qwen3-Embedding-0.6B`**（1024 维，多语言），直接复用本机已有的 HuggingFace 缓存，
  并通过 `HF_HUB_OFFLINE=1` 强制离线，**不会偷偷联网下载**。
- 新增 `embeddings.py` 作为全局单例，`app.py` 与检索层共用同一个实例，不再重复加载。
- 加载失败会带明确原因抛给前端，不再静默降级。
- 相似度改用**余弦相似度**（向量归一化 + 内积索引），符合该模型的训练方式。

实测语义区分度（同一模型内的余弦相似度）：

| 对照 | 相似度 |
|---|---|
| 「医学图像分割」 vs 「medical image segmentation」 | **0.87** |
| 「医学图像分割」 vs 「今天天气不错适合出去散步」 | 0.32 |
| 「本文提出的方法在三个数据集上取得最优性能」 vs 「实验结果表明该方法在三个公开数据集上均达到最好效果」 | **0.89** |
| 「本文提出的方法在三个数据集上取得最优性能」 vs 「超级电容器的工作电压窗口为1.8V」 | 0.27 |

### 2. 可溯源引用

链路：**PyMuPDF 逐页解析 → 按句边界分块并保留页码/章节 → 混合检索 → 重排 → 上下文带页码标记 → 大模型强制标注 `[[p.页码]]` → 前端渲染成可点击按钮 → 右侧原文跳页**

- `retrieval.py::extract_pages` 用 PyMuPDF 逐页提取（v1 用 pdfplumber 抽纯文本，页码在抽取时就丢了）。
- `chunk_pages` 按句子边界切块（约 700 字，带一句重叠），避免把句子拦腰截断，并识别章节标题。
- **混合检索**：向量语义检索 + 纯 Python 实现的 BM25 关键词检索，按 6:4 融合。
  中文用二元字组切分，专有名词、公式符号这类向量模型不敏感的查询命中率明显提高。
- **词面重排**：按查询词在候选块中的覆盖率再做一次加权，提升答案所在段落的名次。
- 大模型侧强制引用规则：页码只能取自给定片段，禁止编造。

### 3. 登录鉴权与多用户隔离

- `auth.py`：密码用 **bcrypt** 加盐哈希（长密码先做 SHA-256 再 base64，规避 bcrypt 72 字节截断），
  会话用 **itsdangerous** 签名令牌，HttpOnly Cookie + `Authorization: Bearer` 双通道。
- 文献按账号隔离到 `uploads/<用户ID>/`，访问别人的文档一律 404。
- **零新增依赖**：bcrypt / itsdangerous 都是本机已装好的。
- 升级前的老文献由**第一个注册的账号**自动继承，并自动重建为带页码的新格式（无损迁移）。

### 4. 前端离线化与体验

- Tailwind、FontAwesome 全部下载到 `vendor/` 本地，**不再依赖任何国外 CDN**。
- 去掉 pdf.js，改用**浏览器原生 PDF 阅读器**：靠 iframe 的 `#page=N` 跳页，
  少一个依赖、少一份下载，断网也能用。
- 摘要、问答、翻译全部改为 **SSE 流式输出**，配打字机光标。
- 索引进度实时显示在左侧文献列表上。

## 三、性能实测

### 向量编码（110 个 700 字片段，约 4.6 万 token）

| 设备 | 耗时 | 换算 |
|---|---|---|
| CPU（20 线程，`torch 2.11.0+cpu`） | 12~35 分钟 | 每块 6~19 秒 |
| **GPU（RTX 4060 Laptop，`torch 2.11.0+cu128`）** | **4.3 秒** | 约 200 倍 |

> 说明：本机 CPU 的矩阵算力并不差（1024³ 矩阵乘实测 486 GFLOPS），
> 瓶颈在于 0.6B 模型 fp32 前向在 CPU 上只能跑到峰值算力的约 15%。
> 测过 `onnxruntime`（本机只有 CPU 版执行提供器）和 torch 动态 int8 量化，均无有效加速。

因为 CPU 上建索引太慢，架构上做了配套设计：

- **上传立即返回**，索引在后台线程构建，前端轮询显示进度条；
- 同时只允许一个索引任务运行，避免多个任务抢 CPU 互相拖慢；
- 显存不足时自动把批次减半重试，不会因为一次 OOM 让整个索引失败。

### 端到端

- 后端 37 项自测全部通过（注册/登录/隔离/上传/索引/流式摘要/溯源问答/原文服务/删除）
- 前端 17 项渲染逻辑单测全部通过
- 11MB 的 PDF，原文服务返回 200，`Content-Type: application/pdf`

## 五、已知限制

1. **扫描版 PDF 不支持**：提取不到文字会明确报错，需要先做 OCR（后续可接入）。
2. **词面重排不是神经网络重排**：本机没有缓存交叉编码器重排模型，当前用查询词覆盖率做重排。
   接入重排模型后精度还能再上一档（需要额外下载模型）。
3. **开发服务器**：目前用 Flask 自带服务器，够本地/小范围使用；要对外发布需换 waitress/gunicorn。
4. **单机存储**：文献以文件形式存在 `uploads/`，没有上数据库；多实例部署需要换存储方案。

## 六、v2.1 补充：多格式上传

原来只支持 PDF，现在扩展到 **PDF / Word(.docx) / Markdown(.md) / 纯文本(.txt)**。

### 关键设计：没有"页"的文档怎么做出处？

项目的招牌是"答案带出处、点一下跳原文"，但 txt / md / docx 没有页码概念。做法是：

| 格式 | 出处单位 | 点出处后的跳转方式 |
|---|---|---|
| PDF | **页**（真实页码） | iframe 跳到 `#page=N` |
| docx / md / txt | **段**（按约 1600 字合成的编号单元） | 右侧渲染正文，滚动定位并高亮该段 |

给大模型的提示词会带上对应单位，所以它会写"依据第 3 段"而不是"第 3 页"。

### 各格式的解析方式

- **docx**：用本机已装的 `python-docx` 读段落。能拿到标题样式，章节识别比纯文本准；
  表格里的文字也会被提取出来。
- **md**：按 `#` 标题和空行分段，标题直接作为章节。
- **txt**：自动识别编码 —— UTF-8（含 BOM）、UTF-16、GB18030（兼容 GBK / GB2312）。
  Windows 上不少文本文件是 GBK 的，不做兜底会直接乱码。

### 顺手修掉的两个真 bug

1. **纯中文文件名会丢扩展名。** Werkzeug 的 `secure_filename` 会把非 ASCII 字符全部剔除，
   `分割研究备忘.txt` 处理完变成 `txt`（连点都没了），存盘后判断不出格式，上传必定失败。
   现在改成"清洗过的文件名主体 + 原始后缀"重新拼。
2. **短内容被整段丢弃。** 原来的切块逻辑有一条"不足 60 字就丢掉"的规则，
   导致 docx 的小标题、表格这类短内容永远进不了索引（搜不到、也不会被引用）。
   现在改成：只有"切块时带上的重叠句"才会被丢弃，真实内容再短也保留。

### 实测

新增 `tests/check_formats.py`，**33 项断言全部通过**，覆盖：GBK 编码的 txt、
Markdown、真实 docx（含标题与表格）、`.doc` 被拒绝、索引构建、正文接口、
带出处的问答与摘要，以及 PDF 不受影响的回归验证。
